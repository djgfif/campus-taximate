# 기능적·비기능적 요구사항 명세 (v2.0)

> **기준일:** 2026-11-25 · **연계 문서:** [service-overview.md](../01-product/service-overview.md) · [use-cases.md](use-cases.md) · [traceability.md](traceability.md) · [architecture-and-policy.md](../03-design/architecture-and-policy.md)

## 작성 원칙
- **UI·API 기준 전수 포함:** 현재 화면과 목표 구조에 존재하는 활성 기능을 누락 없이 적는다.
- **한 항목 = 한 기능 = 한 줄:** 수치 규칙(15분·10%·6자리·6시간)과 내부 구현(스케줄러·DB)은 설계 문서로 분리한다.
- **우선순위 3단계 + Demo 분리:**
  - **P0 (핵심 필수):** 없으면 동승 매칭·비율 분담·후불 1회 결제 서비스가 성립하지 않는 기능
  - **P1 (운영·안전 지원):** 실사용 안전·소통·이력 조회·관리자 운영에 필요한 기능
  - **P2 (부가 편의):** 핵심 흐름과 무관하게 제거·확장 가능한 기능 *(UI 정리 시 축소·제외 검토 대상)*
  - **Demo (시연 전용):** 발표·재현 제어 도구 — 학생 화면과 운영 환경에서 격리

## 4. 프로젝트 핵심 제약사항

1. **법적·운영 범위:** 실제 택시 호출·배차와 결제자 계좌 실송금은 수행하지 않으며, 모의 결제·모의 지급 장부와 공개 데이터 모의실험으로 검증 범위를 한정한다([legal-scope.md](../05-submission/legal-scope.md)).
2. **외부 API 한도:** 카카오모빌리티·TMAP 무료 쿼터 범위 내에서 후보를 제한해 호출하며, API 키가 없는 환경에서는 모의 경로임을 화면에 명시한다.
3. **결제·지급 분리:** 실제 상용 PG 정산은 매입 잔액 확보 및 영업일 08~15시 지급 요청 제약이 있으므로, 시스템은 `정산 확정 / 결제 완료 / 모의 지급` 3개 상태를 분리한다.
