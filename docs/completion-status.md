# 캡스톤 완료 관리표

기준일: 2026-11-19(최종본). 교수님 미팅 11/23, 최종 발표·제출 12/06.

이 문서는 요구사항, 구현, 검증 결과와 외부 자료 의존성을 구분한다. 테스트 통과만으로 실측 정확도나 실제 서비스 운영 가능성을 주장하지 않는다.

11/19 최종본: 실제 MySQL 8.4.3을 포함해 Maven 엔진 73개·서버 480개(실패·건너뜀 0), 프런트 112개·lint·build, 실험 도구 23개가 통과했다. 요금 오차는 팀 실측 대신 공개 실제 운행 기록으로 측정했다(서울 2025, 평가 277,978건, ±15% 이내 88.39%). 11/23 미팅 피드백과 팀원 PC 재현은 다음 단계다. [최종 검증 기록](verification-2026-11-19-final.md), [기능·시연 검증](verification-2026-11-19.md)

## 확정한 규칙

- 탑승번호는 교수 제안이 아닌 팀원 제안이다. 번호 미입력 자체는 노쇼 확정이 아니다.
- 도착·실제 탑승·운행 시작을 구분한다. 번호 입력 기한은 결제자의 실제 탑승 표시부터 5분이다.
- 예약 선결제·무료 취소 마감은 T−20분, 즉시는 확정+5분이다. T+5분 운행 확인과 번호 입력 기한은 서로 다른 규칙이다.
- 결제자 승계 수락만으로 출발하지 않는다. 기존 번호를 폐기하고 새 결제자가 실제 탑승을 표시해야 새 번호를 연다.
- 예약/즉시의 현재 공통 승차점 매칭 범위를 유지한다. 과거 비활성 경로 유형을 다시 활성화하지 않는다.
- 예상 분담금의 여유 15%, 지연 15분, 절감 10% 기준을 실험 결과에 맞춰 임의로 변경하지 않는다.
- 기존 캐시 우선, 신규 카카오 실험 호출 최대 100회. 실측 자료와 합성·대리 자료를 구분한다.
- 지급은 모의 장부다. 실제 지급대행 연동이나 상용 운영을 완료했다고 주장하지 않는다.

## 팀이 제공·확인해야 하는 항목

1. 팀원 실제 탑승 기록 수집은 하지 않는다(11/19 결정). 요금 오차는 공개 실제 운행 기록으로 측정하며, 일반 택시 영수증 검증과 구분해 설명한다.
2. 11/23 미팅 결과를 이 표에 추가하고, 새 요구사항은 기존 교수·팀원·품질 항목과 구분한다.
3. 최종 발표 시간 확정 전에는 5분·10분 두 대본을 유지한다.
4. 최종 발표 전 팀원 PC에서 실행 안내를 따라 재현하고 리허설한다.

## 제출 묶음

- 소스와 설치·실행 안내, API/규칙 문서, 실제 실행한 검증 기록.
- 익명 실측 집계와 재현 실험 보고서, 원본/캐시 출처와 한계.
- 기존 양식을 유지한 PPT·PDF, 발표 대본과 별도 Q&A, 시연 영상.
- `python scripts/release_bundle.py`로 소스 스냅샷과 SHA-256 목록을 만든다. 비밀키·업로드·원본 탑승 자료·빌드 캐시는 포함하지 않는다.
- 작업 트리가 변경된 스냅샷은 커밋 버전이라고 표시하지 않는다. 배포 전 최종 검토·버전 고정과 같은 버전의 실험·발표 결과가 필요하다.
